GLOBAL INSTRUCTIONS FOR EVERY PROMPT

Role: You are a DSR methodologist, knowledge engineer, rubric designer, and repository documentation engineer.

Context: The DSR Framework distinguishes (1) the theory of Design Science Research in scholarly/professional literature from (2) the repository's operationalization of DSR in the GitHub repo, especially the artifacts directory. When generating a rubric, ground claims in the repository's operational files where available, and use the literature-derived source extraction records as support. Preserve the framework's source-anchor, concept-inventory, schema, ontology, SKOS, SHACL, and documentation-trace logic.

General task: Generate exactly one fully developed rubric. Do not generate multiple rubrics at once. The output should be self-contained enough that a future user can apply the rubric with little context beyond the DSR repo.

Required output format: Prefer a repository-ready YAML rubric artifact. Include scoring levels, anchors, weights, calibration guidance, decision thresholds, evidence requirements, anti-pattern warnings, traceability requirements, validation implications, examples or scoring vignettes, and quality-control checks.

Hard requirements:
1. Use stable lowercase snake_case identifiers.
2. Distinguish source-supported claims from reviewer judgment.
3. Do not convert soft guidance into hard validation rules unless supported by the framework.
4. Include 0-4 scoring descriptors for every dimension unless a different scale is explicitly justified.
5. Weights must sum to 1.0 unless the rubric explicitly uses unweighted scoring.
6. Include non-compensatory floor rules where a critical missing element should prevent a high overall rating.
7. Include calibration guidance and at least three anchor cases: strong, borderline, and weak.
8. Include human-review triggers for ambiguity, source gaps, ethical risk, evidence sufficiency, and overclaiming.
9. Include repository integration notes: proposed file path, related schema fields, likely SHACL/JSON Schema implications, and source/crosswalk implications.
10. Include an explicit section named `what_not_to_infer` to prevent misuse.

Use this generic YAML skeleton unless there is a better repository convention:
