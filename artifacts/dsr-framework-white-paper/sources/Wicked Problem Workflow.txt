Below is a practical **Wicked Problem Resolution Workflow** built around your DSR framework logic: move from a messy, situated problem to an evaluated artifact/intervention and codified design knowledge, while preserving traceability from problem → requirement → design decision → evaluation → contribution. Your DSR synthesis defines a DSR study as a traceable process that transforms a relevant problem instance and problem class into an evaluated artifact/design entity and codified design knowledge, with evidence linking problem, requirements, design decisions, evaluation results, contribution claims, and boundary conditions. fileciteturn0file8

# Wicked Problem Resolution Workflow

## 0. Set the operating rule

Treat the wicked problem as something to **navigate and progressively tame**, not something to “solve once.”

Your working rule:

> “I will produce progressively better problem framings, interventions, evaluations, and reusable design knowledge, while documenting what is known, assumed, contested, bounded, and learned.”

This keeps you from prematurely forcing the problem into a linear project plan.

---

## Phase 1 — Capture the problematic situation

| Step | Action | Output |
|---|---|---|
| 1.1 | Write a raw description of the situation without trying to solve it. | **Problem situation note** |
| 1.2 | Identify visible symptoms, harms, bottlenecks, conflicts, and unmet needs. | **Symptom inventory** |
| 1.3 | Separate facts, interpretations, assumptions, and stakeholder claims. | **Claim ledger** |
| 1.4 | Identify what makes the problem wicked: ambiguity, stakeholder conflict, circular causality, no obvious stopping rule, shifting constraints, political/ethical burden, or uncertain evaluation criteria. | **Wickedness profile** |

Use this question:

> “What situation keeps reproducing the unwanted condition, even after reasonable people try to fix it?”

---

## Phase 2 — Define the problem instance and problem class

Your DSR materials emphasize distinguishing a **situated problem instance** from an abstract **problem class**, because reusable design knowledge depends on abstraction beyond a local case. fileciteturn0file34

| Step | Action | Output |
|---|---|---|
| 2.1 | Define the local problem instance: where, for whom, under what constraints, with what consequences. | **Problem instance statement** |
| 2.2 | Abstract the problem class: the recurring type of problem this instance represents. | **Problem class statement** |
| 2.3 | State why the problem matters practically and theoretically. | **Relevance justification** |
| 2.4 | List boundary conditions: where your diagnosis may not apply. | **Boundary-condition register** |

Template:

```text id="5xnsiv"
Problem instance:
In [context], [stakeholders] experience [unwanted condition] because [suspected mechanisms/constraints], resulting in [consequences].

Problem class:
This is an instance of a broader class of problems in which [generalized actors/systems] struggle to [generalized function] under [generalized constraints].

Relevance:
This matters because [severity, frequency, risk, opportunity, stakeholder burden, institutional importance].

Boundary conditions:
This framing applies when [conditions] and may not apply when [conditions].
```

---

## Phase 3 — Map the stakeholder and context system

Wicked problems are usually not just technical problems. They are embedded in context: organizational, social, regulatory, technical, temporal, resource, and governance conditions. The DSR concept inventory treats context, stakeholders, artifact networks, and boundary conditions as core parts of the DSR record. fileciteturn0file35

| Step | Action | Output |
|---|---|---|
| 3.1 | Identify stakeholder groups, not just named individuals. | **Stakeholder map** |
| 3.2 | For each group, document goals, pains, incentives, authority, constraints, and likely resistance. | **Stakeholder profile table** |
| 3.3 | Map contextual constraints: policy, data, systems, culture, budget, time, compliance, ethics, technology. | **Context register** |
| 3.4 | Identify affected artifacts, processes, documents, systems, metrics, and decision rights. | **Artifact/process network map** |

Core diagnostic question:

> “Who benefits from the current structure, who is harmed by it, who can change it, and who must live with the result?”

---

## Phase 4 — Build a causal and structural model

Do not jump from problem to solution. First model why the problem persists.

| Step | Action | Output |
|---|---|---|
| 4.1 | Create a causal map of reinforcing loops, bottlenecks, incentives, dependencies, and failure points. | **Causal loop map** |
| 4.2 | Identify root causes, contributing causes, enabling conditions, and aggravating conditions. | **Causal factor table** |
| 4.3 | Distinguish controllable, influenceable, and uncontrollable factors. | **Control/influence matrix** |
| 4.4 | Identify leverage points where small changes may produce large improvements. | **Leverage-point list** |

Useful categories:

| Category | Meaning |
|---|---|
| Root cause | Necessary underlying driver |
| Contributing cause | Makes the problem worse but is not sufficient alone |
| Enabling condition | Allows the problem to continue |
| Constraint | Limits feasible solutions |
| Symptom | Visible manifestation, not necessarily causal |
| Leverage point | Intervention point with disproportionate effect |

---

## Phase 5 — Translate the problem into objectives and requirements

This is where the workflow becomes design-oriented.

| Step | Action | Output |
|---|---|---|
| 5.1 | Convert the problem into improvement objectives. | **Objective set** |
| 5.2 | Convert objectives into requirements. | **Requirement list** |
| 5.3 | Define acceptance criteria for each requirement. | **Acceptance criteria** |
| 5.4 | Trace each requirement back to a problem factor or stakeholder need. | **Problem → requirement trace matrix** |

Template:

| Problem factor | Objective | Requirement | Acceptance criterion | Stakeholder source |
|---|---|---|---|---|
| Example: inconsistent documentation | Increase documentation reliability | The process must require a reusable evidence trace | 95% of records include source, decision, and evaluation links | QA, reviewers, implementers |

This prevents solution drift.

---

## Phase 6 — Search the solution space

Your DSR synthesis treats the solution space as prior artifacts, theories, technologies, methods, design patterns, and alternatives used to ground the intervention. fileciteturn0file8

| Step | Action | Output |
|---|---|---|
| 6.1 | Identify prior solutions, analogous cases, theories, methods, technologies, and design patterns. | **Input-knowledge inventory** |
| 6.2 | Identify why previous fixes failed or only partially worked. | **Prior-solution critique** |
| 6.3 | Generate multiple candidate interventions, not one preferred solution. | **Solution-option portfolio** |
| 6.4 | Rate each option against feasibility, stakeholder acceptability, ethical risk, reversibility, cost, evidence strength, and expected impact. | **Option evaluation matrix** |

Minimum comparison criteria:

| Criterion | Question |
|---|---|
| Fit | Does it address the actual problem mechanism? |
| Feasibility | Can we implement it with available resources? |
| Acceptability | Will key stakeholders tolerate or support it? |
| Reversibility | Can we undo or revise it safely? |
| Evaluability | Can we know whether it worked? |
| Ethical burden | Who bears the cost, risk, or inconvenience? |
| Knowledge value | What reusable design knowledge could it produce? |

---

## Phase 7 — Design the intervention as an artifact

In DSR terms, avoid saying merely “we implemented a thing.” Specify the **artifact/design entity**, its concrete instantiation, its make plan, use plan, capacity specification, and claims. Your operational synthesis explicitly distinguishes artifact/design entity, artifact instantiation, make plan, use plan, capacity specification, make claim, use claim, and usage-effect claim. fileciteturn0file8

| Step | Action | Output |
|---|---|---|
| 7.1 | Name the designed artifact or intervention. | **Artifact name** |
| 7.2 | Classify it: process, model, method, framework, taxonomy, tool, dashboard, policy mechanism, governance structure, training protocol, knowledge graph, etc. | **Artifact type** |
| 7.3 | Define what it is supposed to make possible. | **Capacity specification** |
| 7.4 | Define how it is produced or maintained. | **Make plan** |
| 7.5 | Define how users are supposed to use it. | **Use plan** |
| 7.6 | State what claims you are making about it. | **Make/use/effect claims** |

Artifact specification template:

```yaml id="wfkjbo"
artifact:
  name:
  artifact_type:
  problem_class_addressed:
  intended_users:
  capacity_specification:
    - capacity:
      success_indicator:
  make_plan:
    steps:
    required_resources:
    maintenance_needs:
  use_plan:
    user_roles:
    use_context:
    use_steps:
  claims:
    make_claim:
    use_claim:
    usage_effect_claim:
  boundary_conditions:
```

## Phase 8 — Run safe-to-fail experiments

For wicked problems, prefer **safe-to-fail probes** over large irreversible reforms.

| Step | Action | Output |
|---|---|---|
| 8.1 | Select a small pilot context. | **Pilot scope** |
| 8.2 | Define what would count as success, partial success, failure, and harmful side effect. | **Evaluation thresholds** |
| 8.3 | Implement the smallest useful version of the artifact. | **Prototype/pilot** |
| 8.4 | Collect evidence from multiple angles: performance, user experience, stakeholder acceptance, unintended consequences, cost, and sustainability. | **Evaluation evidence package** |
| 8.5 | Decide whether to preserve, revise, scale, combine, or abandon the intervention. | **Iteration decision** |

Use this evaluation matrix:

| Claim | Evidence needed | Method | Timing | Stakeholder | Decision rule |
|---|---|---|---|---|---|
| The artifact can be built reliably | Build/conformance evidence | Inspection, walkthrough, test | Ex ante/formative | Implementer | Revise if core capacity absent |
| Users can use it as intended | Use evidence | Pilot, observation, usability test | Ex post/formative | Users | Revise if workarounds dominate |
| It improves the target condition | Effect evidence | Metrics, comparison, case evidence | Ex post/summative | Beneficiaries/sponsors | Scale only if benefit exceeds burden |

---

## Phase 9 — Evaluate claim-evidence alignment

Do not ask only, “Did it work?” Ask, “Which claim is supported by which evidence, under which conditions?”

| Step | Action | Output |
|---|---|---|
| 9.1 | Link every evaluation result to a specific claim. | **Evidence → claim trace** |
| 9.2 | Identify unsupported claims. | **Claim-risk list** |
| 9.3 | Identify context-dependent findings. | **Boundary-conditioned findings** |
| 9.4 | Identify unintended consequences and stakeholder burdens. | **Side-effect register** |
| 9.5 | Decide whether the intervention is effective, promising, inconclusive, harmful, or overclaimed. | **Evaluation judgment** |

Judgment categories:

| Category | Meaning |
|---|---|
| Effective | Evidence supports use under stated conditions |
| Promising | Some evidence supports continued iteration |
| Inconclusive | Evidence is insufficient or mixed |
| Harmful | Intervention worsens key outcomes or burdens stakeholders |
| Overclaimed | Evidence supports a narrower claim than originally stated |

---

## Phase 10 — Codify design knowledge

This is the step that turns problem solving into reusable knowledge.

| Step | Action | Output |
|---|---|---|
| 10.1 | State what was learned about the problem class. | **Problem-class insight** |
| 10.2 | State what was learned about the artifact/intervention. | **Artifact insight** |
| 10.3 | State what worked, for whom, why, and under what conditions. | **Design principle or design proposition** |
| 10.4 | State what did not work and why. | **Negative design knowledge** |
| 10.5 | Package the reusable knowledge for future projects. | **Design knowledge record** |

Design principle template:

```text id="c0o2h3"
For [problem class] in [context/boundary conditions],
use/design [artifact or intervention feature],
because it enables [mechanism/capacity],
which tends to produce [intended outcome],
provided that [conditions/constraints] hold.
```

---

## Phase 11 — Institutionalize, scale, or reframe

| Step | Action | Output |
|---|---|---|
| 11.1 | Decide whether to scale, modify, pause, or abandon. | **Scale decision** |
| 11.2 | Define governance and maintenance responsibilities. | **Ownership model** |
| 11.3 | Update policies, templates, training, systems, or documentation. | **Institutionalization package** |
| 11.4 | Monitor whether the problem mutates. | **Ongoing monitoring plan** |
| 11.5 | Re-enter the workflow if the problem changes. | **Next-cycle trigger** |

Stopping rule:

> Stop the current cycle when the intervention is good enough to preserve, scale, or abandon under explicit evidence and boundary conditions—not when the wicked problem is permanently “solved.”

# Compact checklist version

Use this as the recurring operational checklist:

| Phase | Key question | Required output |
|---|---|---|
| 1. Situation capture | What is happening? | Problem situation note |
| 2. Problem abstraction | What local problem and broader problem class are involved? | Problem instance/class |
| 3. Stakeholder/context mapping | Who is affected, who decides, and what constrains action? | Stakeholder/context register |
| 4. Causal modeling | Why does the problem persist? | Causal/leverage map |
| 5. Requirements | What must improve, and how will we know? | Objective/requirement matrix |
| 6. Solution-space search | What existing knowledge can ground intervention? | Input-knowledge inventory |
| 7. Artifact design | What intervention artifact are we designing? | Artifact specification |
| 8. Safe-to-fail pilot | What small test can generate evidence? | Pilot/evaluation plan |
| 9. Evaluation | Which claims are supported by which evidence? | Claim-evidence matrix |
| 10. Knowledge codification | What reusable design knowledge emerged? | Design knowledge record |
| 11. Institutionalization | Should we scale, revise, stop, or reframe? | Scale/reframe decision |

# Anti-pattern checks

Before moving forward, ask:

| Anti-pattern | Diagnostic question |
|---|---|
| Premature solutioning | Did I choose a solution before modeling the problem? |
| Stakeholder flattening | Did I treat stakeholders as one group with one interest? |
| Localism | Am I only solving a local symptom without abstracting the problem class? |
| Overabstraction | Is the problem class so broad that it no longer guides action? |
| Artifact black box | Have I specified how the intervention works, not just what it is called? |
| Evaluation mismatch | Does my evidence actually test my claim? |
| Success theater | Am I collecting favorable evidence while ignoring burden, resistance, or side effects? |
| No boundary conditions | Am I implying generality without saying where the result applies? |
| No knowledge capture | Did I solve locally without producing reusable design knowledge? |

# Minimal weekly cadence

A simple cadence you can actually follow:

| Week | Focus | Main artifact |
|---|---|---|
| Week 1 | Situation, stakeholders, context | Problem/context brief |
| Week 2 | Problem instance/class and causal model | Problem-class and causal map |
| Week 3 | Objectives, requirements, solution search | Requirement and solution matrix |
| Week 4 | Artifact/intervention design | Artifact specification |
| Week 5 | Pilot/evaluation setup | Evaluation protocol |
| Week 6 | Safe-to-fail implementation | Pilot evidence |
| Week 7 | Evaluation and learning | Claim-evidence matrix |
| Week 8 | Codification and next decision | Design knowledge record |

The full workflow can be recursive: after Week 8, you either scale, revise, abandon, or reframe and begin another cycle.
